# Milestone 3 / Feature B — On-chain Escrow Contract (Design Spec)

> Date: 2026-05-20
> Status: design draft, pending user review.
> Cross-cutting decisions: see `2026-05-20-milestone-3-overview.md`.
> Depends on feature A's chain plumbing (`src/lib/cardano/{network,u5c-client,signer}.ts`).

## Goal

Hold buyer funds in an on-chain script address until a shipping-related event releases them to the merchant (happy path) or returns them to the buyer (no-ship timeout). Funds move only through validator-authorised redeemers; no party holds the funds unilaterally between lock and release.

Maps to grant outputs:
- **B1** — escrow contract holds funds between buyer and seller until released by a shipping-related event.
- **B2** — link to on-chain transactions for 2 tested release scenarios.

## Approach

A Plutus validator written in **Aiken** locks the buyer's payment with a structured datum and exposes three redeemers: `MarkShipped`, `Release`, `Refund`. The UTxO transitions through two on-chain states (Pending → Shipped) before the merchant can withdraw; the buyer can refund only while the UTxO is still Pending and after the ship deadline has passed.

All orders use escrow in milestone scope — the direct payment to the merchant is removed and replaced by a lock to the script address.

### Why this shape

- **On-chain state machine** (Pending → Shipped → Released/Refunded) makes "the merchant cannot release without first shipping" an on-chain rule, not an off-chain promise.
- **Two paths, no arbitrator** (release + refund) keeps the validator small and gives the milestone two clean, testable scenarios.
- **Value-agnostic validator** — Aiken does not inspect what tokens are locked; the tx builder is responsible for moving full value to the recipient. Supports ADA and Cardano native tokens uniformly.
- **Datum-encoded timeouts** — `ship_deadline` and `grace_period_end` live in the datum, so the merchant cannot retroactively shorten the buyer's window after lock.

## Validator

### Datum

```aiken
type EscrowDatum {
  buyer: VerificationKeyHash,
  merchant: VerificationKeyHash,
  order_id: ByteArray,           // DB UUID, 16 bytes
  paid_at: PosixTime,            // lock-tx slot, captured at lock time
  ship_deadline: PosixTime,      // paid_at + ship_window
  grace_period_end: Option<PosixTime>,  // None in Pending; Some(t) in Shipped where t = shipped_at + grace_period
}
```

The Pending/Shipped state distinction is carried by `grace_period_end`:
- `None` → Pending (just locked, awaiting shipment).
- `Some(t)` → Shipped (merchant has marked shipment; release allowed at slot ≥ t).

### Redeemers

```aiken
type EscrowRedeemer {
  MarkShipped { shipped_at: PosixTime }
  Release
  Refund
}
```

### Rules

| Redeemer | Required state | Required signer | Time constraint | Output constraints |
|---|---|---|---|---|
| `MarkShipped { t }` | `grace_period_end == None` | `merchant` | `t ∈ [tx.valid_from, tx.valid_to]`; `t < ship_deadline` | Single output re-locked at the same script address with the same value, datum mutated only at `grace_period_end = Some(t + grace_period_constant)`. All other datum fields unchanged. |
| `Release` | `grace_period_end == Some(t)` | `merchant` | `tx.valid_from >= t` | Validator does not constrain outputs — the tx builder routes the full UTxO value to the merchant. |
| `Refund` | `grace_period_end == None` | `buyer` | `tx.valid_from >= ship_deadline` | Validator does not constrain outputs — the tx builder routes the full UTxO value to the buyer. |

### Why these guarantees

- The merchant **cannot** release without first shipping (Release requires `Some(_)`).
- The buyer **cannot** refund after the merchant has shipped (Refund requires `None`).
- The merchant **cannot** retroactively shorten the buyer's refund window (datum is immutable except for `grace_period_end`, and only MarkShipped can set it).
- `MarkShipped` cannot lie about when shipment happened (the `shipped_at` in the redeemer is clamped to the tx's validity range, which is at most minutes wide).

### `escrows` schema

```sql
CREATE TABLE escrows (
  id                   UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  order_id             UUID NOT NULL UNIQUE REFERENCES orders(id) ON DELETE CASCADE,
  script_address       TEXT NOT NULL,
  utxo_tx_hash         TEXT NOT NULL,
  utxo_output_index    INTEGER NOT NULL,
  status               TEXT NOT NULL CHECK (status IN ('pending','shipped','released','refunded')),
  buyer_pkh            TEXT NOT NULL,
  merchant_pkh         TEXT NOT NULL,
  paid_at              TIMESTAMPTZ NOT NULL,
  ship_deadline        TIMESTAMPTZ NOT NULL,
  grace_period_end     TIMESTAMPTZ NULL,
  datum_cbor           TEXT NOT NULL,
  shipped_tx_hash      TEXT NULL,
  release_tx_hash      TEXT NULL,
  refund_tx_hash       TEXT NULL,
  created_at           TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at           TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX escrows_status_idx ON escrows(status);
CREATE INDEX escrows_ship_deadline_idx ON escrows(ship_deadline) WHERE status = 'pending';
```

`utxo_tx_hash` + `utxo_output_index` point to the current UTxO; they are updated on every state transition. `datum_cbor` is the hex-encoded CBOR of the current datum, kept so scripts can rebuild transactions without re-deriving from chain.

## Data flow

### Scenario 1 — Buyer pays (lock into escrow)

1. Buyer completes checkout and signs with CIP-30. `cardano-payment.ts` invokes `lock_escrow_ada` (or `lock_escrow_tokens`) via tx3-sdk with `quantity`, `buyer_pkh`, `merchant_pkh`, `order_id`, and the env-configured timeouts.
2. tx3 resolves the tx: buyer input covers `quantity + min_utxo + fees`; output goes to the script address with datum `EscrowDatum { buyer, merchant, order_id, paid_at = now, ship_deadline = now + ESCROW_SHIP_DEADLINE_SECONDS, grace_period_end = None }`.
3. CIP-30 wallet signs. tx submitted via u5c. `waitForConfirmed(PollConfig.default())`.
4. Frontend POSTs to `submitPayment` server-fn with `{orderId, lockTxHash, lockOutputIndex, datumCbor}`.
5. Server-fn, in one SQL transaction:
   - `INSERT INTO escrows (...) VALUES (..., status='pending')`.
   - `UPDATE orders SET status='paid', cardano_tx_hash = lockTxHash`.
   - `INSERT INTO order_events (event_type='paid', tx_hash=lockTxHash, payload, submitted_at, confirmed_at=NOW())`.
6. Frontend redirects to order-confirmation; UI renders escrow state + timeline.

### Scenario 2 — Merchant marks shipped (Pending → Shipped)

1. Operator runs `pnpm tsx scripts/escrow-mark-shipped.ts --order-id <uuid> --tracking <code>`.
2. Script:
   - `SELECT ... FOR UPDATE` on `escrows`. Asserts `status='pending'` and `NOW() < ship_deadline`.
   - Builds `mark_shipped(escrow_utxo)` via tx3-sdk. Input: current escrow UTxO + merchant input for fees. Output: same script address with same value, datum mutated only at `grace_period_end = Some(now + ESCROW_GRACE_PERIOD_SECONDS)`. Redeemer: `MarkShipped { shipped_at = now }`. Metadata under label 1337: `{event:"shipped", order_id, ts, data:{tracking_number}}`.
   - Signs with backend signer (merchant). Submits, `waitForConfirmed`.
3. SQL transaction:
   - `UPDATE escrows SET status='shipped', utxo_tx_hash=<new>, utxo_output_index=<new>, grace_period_end=<calc>, shipped_tx_hash=<hash>, datum_cbor=<new>`.
   - `UPDATE orders SET status='shipped'`.
   - `INSERT INTO order_events (event_type='shipped', tx_hash=<hash>, payload)`.
4. Submission failure → SQL rollback; status unchanged.

### Scenario 3 — Merchant releases (happy path)

1. Operator runs `pnpm tsx scripts/escrow-release.ts --order-id <uuid>`.
2. Script:
   - `SELECT ... FOR UPDATE`. Asserts `status='shipped'` and `NOW() >= grace_period_end`.
   - Builds `release_escrow(escrow_utxo)`: input is the Shipped UTxO + merchant input for fees, output is full value to the merchant. Redeemer: `Release`. Metadata: `{event:"completed", order_id, ts}`. `validity_range.from = NOW()` so the validator can check `tx.valid_from >= grace_period_end`.
   - Signs, submits, `waitForConfirmed`.
3. SQL transaction:
   - `UPDATE escrows SET status='released', release_tx_hash=<hash>`.
   - `UPDATE orders SET status='completed'`.
   - `INSERT INTO order_events (event_type='completed', tx_hash=<hash>, payload)`.

### Scenario 4 — Buyer refunds (no-ship timeout)

1. Operator (with the test buyer key) runs `pnpm tsx scripts/escrow-refund.ts --order-id <uuid> --buyer-key <hex>`.
2. Script:
   - `SELECT ... FOR UPDATE`. Asserts `status='pending'` and `NOW() >= ship_deadline`.
   - Builds `refund_escrow(escrow_utxo)`: input is the Pending UTxO + buyer input for fees, output is full value to the buyer. Redeemer: `Refund`. Metadata: `{event:"cancelled", order_id, ts, data:{reason:"ship_deadline_exceeded"}}`. `validity_range.from = NOW()`.
   - Signs with the buyer key passed in, submits, `waitForConfirmed`.
3. SQL transaction:
   - `UPDATE escrows SET status='refunded', refund_tx_hash=<hash>`.
   - `UPDATE orders SET status='cancelled'`.
   - `INSERT INTO order_events (event_type='cancelled', tx_hash=<hash>, payload)`.

### UTxO ↔ DB synchronisation

Each valid redeemer consumes the current UTxO; MarkShipped also creates a new one. If the DB is not updated atomically with confirmation, the next script cannot find the expected UTxO. Protections:
- All transitions use `SELECT ... FOR UPDATE` on `escrows`.
- The DB write happens inside the same SQL transaction that persists the event row.
- If `waitForConfirmed` times out, the script aborts without writing to DB. The tx may eventually confirm; `reconcile-escrow` then resyncs.

## Error handling

| Failure | Detection | Response |
|---|---|---|
| Buyer cancels sign in CIP-30 during lock | Wallet rejects | UI toast "Pago cancelado". No DB write. Order stays in `pending` (cleaned later by `order-cleanup`). |
| Lock tx rejected by node | u5c error | UI toast with node error. Buyer can retry. |
| Backend signer out of UTxOs for fees | u5c can't find merchant UTxO for fees + collateral | Script aborts `MERCHANT_FUNDS_INSUFFICIENT`. Operator funds the address and retries. |
| MarkShipped attempted after `ship_deadline` | Script pre-check | Aborts `SHIP_DEADLINE_EXCEEDED`. On-chain transition is impossible; buyer's refund path is the resolution. |
| Release attempted before `grace_period_end` | Script pre-check | Aborts `GRACE_PERIOD_NOT_ELAPSED`. Operator waits. |
| Race: buyer Refund vs merchant MarkShipped | One enters ledger; the other UTxO is consumed | Loser script gets `MissingUtxo` from node; aborts without DB write. `reconcile-escrow` resyncs from chain state. |
| Script crashes between submit and DB commit | UTxO consumed on-chain; DB still shows old state | `reconcile-escrow`: for each `escrows` row whose `utxo_tx_hash` is no longer at the script address, scan outputs matching the order_id, update the row, and insert any missing event row. |
| Datum mismatch (DB vs chain) | Script re-fetches UTxO before tx build; mismatch detected | Abort `DATUM_MISMATCH`. Manual investigation. |
| Validator rejects on slot range | Mismatch between server clock and node slot | Set `valid_from = NOW()`, `valid_to = NOW() + 1h`. If skewed, sync clock or read slot from u5c. |
| Multi-asset: full value must move | Validator doesn't enforce | Tx builder includes the full input value in the destination output. Test `escrow_with_tokens.e2e.ts` covers this. |
| Min-ADA in script UTxO with tokens | Native tokens require min-ADA in the UTxO | `lock_escrow_tokens` adds `min_utxo` ADA alongside the token bundle. Min-ADA travels with the bundle on Release/Refund. |

## Validator edge cases (covered by Aiken tests)

1. **MarkShipped mutating disallowed datum fields** — output datum must equal input datum except for `grace_period_end`. Any other change → fail.
2. **Release without prior MarkShipped** — `grace_period_end == None` → fail.
3. **Refund after MarkShipped** — `grace_period_end == Some(_)` → fail.
4. **MarkShipped with `shipped_at` outside tx validity range** → fail.
5. **Spending the UTxO with an unsupported redeemer** — CBOR rejected by validator deserializer.

## Idempotency

- `escrows.order_id` is UNIQUE → one escrow per order.
- Each transition checks current status before building; same transition twice on the same row is rejected pre-submit.
- Crashes between submit and commit are recoverable by `reconcile-escrow`.

## Testing strategy

### Aiken unit tests (`aiken check`)

Validator-level invariants tested in `aiken/validators/escrow.ak` test blocks:

| Test | Asserts |
|---|---|
| `mark_shipped_success` | Pending UTxO + `MarkShipped{t}` + merchant sig + re-locked output with correct datum → valid. |
| `mark_shipped_wrong_signer` | Buyer signs MarkShipped → invalid. |
| `mark_shipped_shipped_at_outside_range` | `shipped_at` outside `[valid_from, valid_to]` → invalid. |
| `mark_shipped_datum_mutated` | Any datum field other than `grace_period_end` differs → invalid. |
| `mark_shipped_already_shipped` | Input already in Shipped state → invalid. |
| `release_success` | Shipped UTxO + `Release` + merchant sig + `valid_from >= grace_period_end` → valid. |
| `release_before_grace_period` | `valid_from < grace_period_end` → invalid. |
| `release_pending_state` | Input in Pending + `Release` → invalid. |
| `release_wrong_signer` | Buyer signs Release → invalid. |
| `refund_success` | Pending UTxO + `Refund` + buyer sig + `valid_from >= ship_deadline` → valid. |
| `refund_before_deadline` | `valid_from < ship_deadline` → invalid. |
| `refund_shipped_state` | Input in Shipped + `Refund` → invalid. |
| `refund_wrong_signer` | Merchant signs Refund → invalid. |

CI integration: `.github/workflows/aiken-check.yml` runs `aiken check` on PRs touching `aiken/`.

### E2E against dolos

Fixture seeds `@buyer` and `@merchant` addresses with UTxOs. Tests use short timeouts (`ESCROW_SHIP_DEADLINE_SECONDS=60`, `ESCROW_GRACE_PERIOD_SECONDS=60`) and advance dolos slots on demand.

| Test | Asserts |
|---|---|
| `escrow_happy_release.e2e.ts` | lock → +61s → mark-shipped → +61s → release. `orders.status='completed'`, `escrows.status='released'`, 3 event rows. |
| `escrow_refund_timeout.e2e.ts` | lock → +61s → refund. `orders.status='cancelled'`, `escrows.status='refunded'`. |
| `escrow_refund_after_shipped_fails.e2e.ts` | lock → mark-shipped → refund attempt fails. |
| `escrow_release_before_grace_fails.e2e.ts` | lock → mark-shipped → release without slot advance aborts. |
| `escrow_double_mark_shipped_fails.e2e.ts` | Second mark-shipped aborts on state check. |
| `escrow_reconcile_after_crash.e2e.ts` | Manual on-chain transition without DB write → `reconcile-escrow` restores DB consistency. |
| `escrow_with_tokens.e2e.ts` | Happy release with a native token bundle; tokens + min-ADA arrive at merchant. |

## Open questions / future improvements

- **Buyer-facing refund UI** — milestone-mode uses a CLI with a test key. Production needs a "Claim refund" button on the order-confirmation page that opens the CIP-30 wallet and signs the Refund tx.
- **Dispute path** — currently the buyer has no recourse after MarkShipped except off-chain conversation. A future arbitration model (2-of-3 with platform key) is intentionally out of scope.
- **Partial release** — the validator releases full value; a future iteration could allow partial release for partial shipments.
- **Configurable per-order timeouts** — currently all orders share `ESCROW_SHIP_DEADLINE_SECONDS` and `ESCROW_GRACE_PERIOD_SECONDS` from env. Per-product or per-merchant overrides are future work.
- **Scheduled `reconcile-escrow`** — manual script in milestone-mode; should be scheduled in production.
